Agentic AI Engineering Study Book

Reliability, Security, Observability, and Cost Architecture

Interview answer (say this first). Reliability, security, observability, and cost are not four features you add at the end; they are four constraints on the same request path, and the architecture is how you satisfy all four at once. Reliability keeps the system serving when parts fail: timeouts, bounded retries, circuit breakers, bulkheads, graceful degradation, and fallbacks. Security decides who may cross which boundary and what they may do on the far side: trust boundaries, least privilege, a gateway that enforces policy, and human approval gates for irreversible actions. Observability is how you know what happened: traces, metrics, logs, and evals, wired to alerts that page a person. Cost control keeps the unit economics sane: budgets, quotas, caching, model routing, and right-sizing. The senior move is to name the conflicts between them — retries raise cost, caching cuts cost but can leak data and serve stale answers, stricter security adds latency — and to choose deliberately, with a number behind each choice.

Note:

Verified. Every runnable example on this page was executed offline in plain Python (Python 3.14), and each # comment shows the value the code actually prints. No model calls were made, and every number is computed from the formula on the page rather than quoted from a vendor. The YAML and JSON snippets were parsed with a standard parser.

Why this exists

A system that works in a demo and fails in production usually fails in one of these four directions, and the failure is always blamed on the wrong one.

  • Reliability: a slow dependency held every worker, so one bad service took down the whole system. No timeout, no bulkhead.
  • Security: an agent with a broad credential read a document it should never have seen, because retrieval filtered after fetching, not before.
  • Observability: the dashboard showed 99.99% uptime while users complained answers were wrong, because nobody measured answer quality.
  • Cost: one runaway agent looped for a day and spent a month of budget, because no per-task ceiling existed.

The common thread is that each concern was treated as a later task. “We will add monitoring.” “We will lock it down before launch.” “We will optimise cost when the bill arrives.” By then the shape of the system is fixed, and each concern becomes a patch on a design that ignored it.

This page treats the four as cross-cutting architecture: they apply to every component, they interact, and they must be designed together with the request path.

The one-sentence purpose. Treat reliability, security, observability, and cost as four constraints on one request path, because a choice that fixes one usually moves the other three.

Start from zero

Learn these words first. They are used loosely in conversation and precisely in interviews.

Three distinctions matter most:

  • Reliability vs availability. Availability asks “did it respond?” Reliability asks “did it respond correctly, and does it keep doing so when parts fail?” An agent can be 100% available and still unreliable in the way users feel.
  • Observability vs monitoring. Monitoring checks known questions with pre-built dashboards. Observability lets you ask new questions about a request that failed in a way you did not predict. Traces with high-cardinality attributes are what make that possible.
  • Security vs safety. Security protects the system and its data from attackers and mistakes. Safety protects users and the world from the system’s outputs. Prompt injection into a tool call is a security problem; a harmful answer is a safety problem. Both need controls, but they are different controls.

The core idea

Think of a building, not a program.

The request path is the corridor people walk: client, gateway, orchestrator, model, tools, database, and back. Along the corridor there are locked doors (trust boundaries), fuses (circuit breakers), fire doors (bulkheads), cameras (observability), and an electricity meter (cost). You do not install the locks after the corridors are built, because the walls decide where the doors can be.

The mental model is: the request path is the spine, and each concern wraps the whole spine.

Each concern touches every hop, not one box. A timeout belongs at the gateway and at the model call and at the tool call. A trust boundary exists at every hop where data crosses from one level of trust to another. The part interviewers probe is that these four conflict. Every fix moves the others:

The mental model in one line. The request path is the spine; reliability, security, observability, and cost are four forces pulling on it, and every design choice trades one against the others.

A second mental model is the degradation ladder. When something breaks, you do not jump from “perfect” to “error”; you step down.

flowchart LR
    P["1. Full quality<br/>best model, fresh retrieval"] --> A["2. Cheaper model<br/>cached retrieval"]
    A --> B["3. Cached or partial answer<br/>with a warning"]
    B --> C["4. Queue the task<br/>answer later"]
    C --> D["5. Honest failure<br/>typed error, not a guess"]

Every step down is a design decision you make in advance. An agent that has a ladder survives a model-region outage; one that does not has a binary outcome: perfect or down.

How it works

Follow one request through the design, concern by concern.

  1. Draw the request path and its trust boundaries first. Name every hop and mark where the level of trust changes: user to gateway, gateway to orchestrator, orchestrator to model, model to tool, tool to database. Controls live at boundaries, not randomly inside them.
  2. Set a latency budget and a timeout per hop. Give the whole request a budget, split it across hops, and give each hop a timeout slightly smaller than the remainder. A timeout larger than the remaining budget is decoration.
  3. Retry only what is safe and only with a cap. Retry idempotent, transient failures. Use exponential backoff with jitter. Cap attempts and total retry time. Never retry a non-idempotent write without an idempotency key.
  4. Add circuit breakers. When a dependency’s error rate crosses a threshold over a window, open the breaker and fail fast. Probe with a half-open state. This stops retry storms and frees capacity.
  5. Add bulkheads. Give each workload its own concurrency limit, thread pool, or queue, so a slow tool cannot consume every worker the model path needs.
  6. Define the degradation ladder. For each dependency, write the fallback: a smaller model, a cached answer, a queued job, or a typed failure. Choose which one users see and label it so nobody mistakes a degraded answer for a full one.
  7. Enforce least privilege at the gateway. Authenticate the caller, resolve their tenant and roles, and authorise every tool and data access against that identity. The model never holds credentials it can be tricked into using outside policy.
  8. Put approval gates in front of irreversible actions. Sending money, deleting data, emailing customers, and writing to production systems are the four classic gates. The agent proposes; a human disposes.
  9. Instrument traces, metrics, and logs. One trace per request, with spans per hop and attributes for tenant, model, prompt version, token counts, cost, and outcome. Redact secrets and PII at the source.
  10. Add evals as a first-class signal. Unit tests for behaviour, an offline eval set for quality, and sampled online judging. Treat quality as an SLI with a target.
  11. Alert on symptoms a user feels. Page on burn rate for availability, latency, and quality — burn rate is how fast you consume an error budget relative to the rate that would exhaust it exactly at the end of the window, so 1.0 means on pace and 2.0 means you run out in half the period — not on every internal blip. Every alert needs an action and an owner.
  12. Set budgets and quotas before launch. A per-request token ceiling, a per-task cost ceiling, a per-tenant monthly quota, and a global daily kill switch. Cost is a reliability signal for agents.
  13. Cache deliberately and know the keys. Cache embeddings by content hash, answers by normalised question, and retrieval by tenant plus query. State the freshness contract and the invalidation rule.
  14. Route and right-size continuously. Send easy requests to cheap models, reserve the strong model for hard ones, and size GPU capacity from measured tokens per second rather than a guess. The headline: reliability, security, observability, and cost share one object model — the request path — and one unit of account — the successful task. Design them together or pay three times.

The syntax you will use

These are real production forms. Read them once; later chapters explain each.

A resilience policy in YAML. Timeouts, bounded retries, and a breaker, declared once and applied per dependency.

# resilience-policy.yaml - per-dependency reliability settings
dependencies:
  model_gateway:
    timeout_ms: 8000          # hard ceiling for one call
    retries: 1                # one retry only: cheap, idempotent read
    backoff: { base_ms: 200, max_ms: 2000, jitter: true }
    breaker: { error_rate: 0.05, window_s: 30, half_open_requests: 3 }
  vector_store:
    timeout_ms: 300            # retrieval is fast or it is useless
    retries: 2
    backoff: { base_ms: 50, max_ms: 400, jitter: true }
    breaker: { error_rate: 0.10, window_s: 30, half_open_requests: 5 }
  billing_write:
    timeout_ms: 2000
    retries: 0                # non-idempotent write: never retried blindly
    requires_idempotency_key: true

The important line is retries: 0 on the write. Retrying a non-idempotent side effect without a key is how you charge a customer twice.

A quota and cost policy in JSON. Limits that a gateway or agent runtime enforces.

{
  "tenant": "acme",
  "limits": {
    "requests_per_minute": 600,
    "tokens_per_request": 8000,
    "cost_per_task_usd": 0.75,
    "cost_per_day_usd": 250
  },
  "on_exceed": {
    "tokens_per_request": "reject_with_error",
    "cost_per_task_usd": "stop_and_escalate",
    "cost_per_day_usd": "switch_to_cached_and_queue"
  },
  "alert_at_fraction": [0.5, 0.8, 1.0]
}

A limit without a stated action is a dashboard. The action is the architecture.

The cost ceiling in code. Enforce the per-task budget inside the agent loop, not after the invoice.

def task_within_budget(spent_usd: float, next_call_usd: float, limit_usd: float) -> bool:
    return spent_usd + next_call_usd <= limit_usd

print(task_within_budget(0.50, 0.20, 0.75))   # True
print(task_within_budget(0.70, 0.20, 0.75))   # False -> stop and escalate

Checking before each call is what stops a runaway loop from discovering its ceiling on the bill.

Golden signals in PromQL. Latency, traffic, errors, and saturation for a model path.

# p95 latency of successful generations
histogram_quantile(0.95, sum(rate(gen_latency_seconds_bucket[5m])) by (le))

# error ratio
sum(rate(gen_requests_total{outcome="error"}[5m])) / sum(rate(gen_requests_total[5m]))

# saturation: queue depth against the configured limit
sum(inflight_requests) / sum(inflight_limit)

Four signals cover most incidents. A dashboard with two hundred panels covers none.

A trace span with the attributes that matter. The trace is the observability backbone.

with tracer.start_as_current_span("agent.tool_call") as span:
    span.set_attribute("tenant.id", tenant_id)
    span.set_attribute("agent.name", "support_agent")
    span.set_attribute("tool.name", "lookup_order")
    span.set_attribute("model.name", model_id)
    span.set_attribute("gen.prompt_version", prompt_version)
    span.set_attribute("gen.tokens", tokens_used)
    span.set_attribute("gen.cost_usd", cost)
    span.set_attribute("outcome", "success")

Prompt version, tenant, model, cost, and outcome are the five attributes that turn a trace into an answer.

A content-hash cache key. Deterministic, so two identical inputs share one cached result.

import hashlib

def cache_key(tenant: str, model: str, prompt: str, version: str) -> str:
    material = "\x1f".join([tenant, model, version, prompt])
    return hashlib.sha256(material.encode()).hexdigest()

Two things matter: the tenant is in the key (so caches never cross tenants), and the prompt version is in the key (so a prompt change cannot serve a stale result).

An approval gate as a typed decision. The agent proposes an action; policy returns a verdict.

def gate(action: dict, risk: str) -> str:
    if risk == "irreversible":
        return "require_human_approval"
    if risk == "reversible_external":
        return "allow_with_audit"
    return "allow"

Encoding the rule once means every tool call gets the same answer.

Examples: simple to real

Example 1 — the latency budget across a request chain. A timeout is only meaningful against a budget. Here a 1,500 ms budget is split across the hops.

def latency_budget(stages: dict, total_budget_ms: int):
    spent = sum(stages.values())
    return spent, total_budget_ms - spent

stages = {
    "auth": 20, "input_guardrail": 30, "retrieve": 110, "rerank": 90,
    "model_ttft": 400, "model_decode": 700, "output_guardrail": 50,
}
spent, slack = latency_budget(stages, 1500)
print("spent:", spent, "ms  slack:", slack, "ms")
print("model decode share:", stages["model_decode"] / spent)   # 0.5

This chain spends 1,400 ms and leaves 100 ms of slack. Model decode is half the time spent, so a timeout on retrieval longer than the remaining 100 ms is already broken. Setting timeouts without this table is guesswork.

Example 2 — retry amplification. Each retry multiplies load on a struggling service. Jitter and a cap are what keep a blip from becoming an outage.

def retry_stats(p_fail: float, retries: int):
    attempts = retries + 1
    all_fail = p_fail ** attempts
    expected = sum(p_fail ** i for i in range(attempts))
    return attempts, round(all_fail, 5), round(expected, 4)

print("p=0.10 r=2:", retry_stats(0.10, 2))   # (3, 0.001, 1.11)
print("p=0.10 r=4:", retry_stats(0.10, 4))   # (5, 1e-05, 1.1111)
print("p=0.30 r=2:", retry_stats(0.30, 2))   # (3, 0.027, 1.39)

At a 10% failure rate, two retries cut the chance all attempts fail from 10% to 0.1%, at the price of 1.11 calls per request. At a 30% failure rate, the same retries cost 1.39 calls each — and if the failure is a capacity problem, that extra 39% is exactly what keeps the service down. Retry the transient; shed load on the saturated.

Example 3 — the circuit breaker decision. A breaker watches a window and trips past a threshold.

def breaker_state(successes, failures, min_requests=50, error_threshold=0.05):
    total = successes + failures
    if total < min_requests:
        return "closed (insufficient data)"
    rate = failures / total
    return ("open" if rate >= error_threshold else "closed") + f" (rate {rate:.1%})"

print(breaker_state(980, 20))    # closed (rate 2.0%)
print(breaker_state(900, 100))   # open (rate 10.0%)
print(breaker_state(35, 10))     # closed (insufficient data)
print(breaker_state(9995, 5))    # closed (rate 0.1%)

The min_requests guard is the subtle part. Ten requests with two failures is 20% but too little evidence to trip; tripping on it would flap the breaker continuously. A breaker without a minimum-sample floor is an alarm, not a control.

Example 4 — cost budget burn, the same shape as an SLO burn rate. A daily budget with an intra-day projection catches runaway spend early.

def budget_burn(daily_budget_usd, spent_usd, hours_elapsed):
    projected = spent_usd / hours_elapsed * 24
    return {
        "burn": round(spent_usd / daily_budget_usd, 3),
        "projected_usd": round(projected, 2),
        "projected_pct": round(projected / daily_budget_usd * 100, 1),
    }

print(budget_burn(500.0, 180.0, 6))    # burn 0.36, projected 720.0 -> 144.0%
print(budget_burn(500.0, 300.0, 18))   # burn 0.60, projected 400.0 -> 80.0%
print(budget_burn(500.0, 250.0, 12))   # burn 0.50, projected 500.0 -> 100.0%

At hour 6 the burn looks mild at 36% of the daily budget, but the run rate projects to 144% of it. At hour 18, 60% spent projects to a comfortable 80%. The projection, not the raw spend, is the signal. Alert on the projection.

Example 5 — what a cache buys. A cache cuts cost and latency at the price of freshness and a new correctness risk.

def cache_cost(requests, hit_rate, model_cost, lookup_cost):
    misses = requests * (1 - hit_rate)
    return misses * model_cost + requests * lookup_cost

no_cache = cache_cost(1_000_000, 0.0, 0.02, 0.0)      # 20000.0
with_cache = cache_cost(1_000_000, 0.30, 0.02, 0.0002)  # 14200.0
print("saving:", round((no_cache - with_cache) / no_cache * 100, 1), "%")  # 29.0%

avg_latency_with_cache = 0.70 * 900 + 0.30 * 5          # 631.5 ms
print("avg latency:", avg_latency_with_cache, "ms")     # 631.5

A 30% hit rate saves 29% of spend and cuts average latency from 900 ms to 631.5 ms. Now the costs: a stale answer served as fresh, a cache key that omits the tenant, and a hit rate high enough that your quality evals stop seeing real traffic. A cache is a correctness decision disguised as a performance one.

Example 6 — routing by difficulty. Send easy requests to the cheap model and hard ones to the strong model. The blend is the number that matters.

def routed_cost(requests, cheap_share, cheap_cost, strong_cost):
    return requests * (cheap_share * cheap_cost + (1 - cheap_share) * strong_cost)

always_strong = routed_cost(1_000_000, 0.0, 0.002, 0.02)   # 20000.0
routed = routed_cost(1_000_000, 0.70, 0.002, 0.02)          # 7400.0
print("saving:", round((always_strong - routed) / always_strong * 100, 1), "%")  # 63.0%

A 70/30 split saves 63%. The hidden cost is the router’s own error: every request it sends to the cheap model that should have gone to the strong one is a quality regression. Measure that misroute rate and treat it as a quality SLI, not a cost trick.

In production

  • Budget reliability, don’t promise it. “Reliable” means a number: an SLO, an error budget, and a breaker threshold. Every claim in a design review should be checkable.
  • Timeouts must nest. The outer timeout must be larger than the sum of the inner ones plus overhead, or the outer one fires first and you lose the useful error. Draw the budget table before writing config.
  • Retries need three guards: idempotency, a cap, and jitter. Missing any one turns a transient failure into an incident. The write path is where teams get burned.
  • A circuit breaker is a capacity tool as much as a reliability tool. Failing fast frees workers that would otherwise be blocked on a slow dependency, which is what keeps the rest of the system up.
  • Bulkheads stop the “one slow tool” outage. Give the model path, each tool class, and each tenant their own concurrency limits. A shared pool means the noisiest caller sets everyone’s latency.
  • Degrade before you fail. A cached, clearly-labelled answer beats a 500. But label it: an unmarked degraded answer destroys trust faster than an honest error.
  • Put the cheapest control first. Input validation, schema checks, and allowlists are cheap and catch most mistakes. Model-based guardrails are slower and costlier; add them after the cheap ones.
  • The model is a trust boundary, not a trusted component. Treat model output as untrusted input to the next system. Every tool call re-checks authorisation against the user’s identity, never the model’s word.
  • Log decisions, not secrets. Record which policy fired, which model, and which tools, but redact credentials and PII at the source. A log store that holds raw tokens is a breach waiting to happen.
  • Observability must be trace-first for agents. A single request can make dozens of model and tool calls. Without a trace you cannot reconstruct what the agent did or why.
  • Cost is a first-class SLI for agents. Track cost per successful task, not cost per call. A cheap model that fails often can be the expensive choice.
  • Review the four together every quarter. A cost cut that doubles incident rate, or a security control that triples latency, is a net loss. The review is where you notice.

The review question. For any new feature, ask four questions in order: what is the failure mode, what is the trust boundary, how will we see it, and what does it cost per successful task? A design that cannot answer all four is not ready.

Interview questions

1. How do you make an LLM system reliable when a model provider goes down?

Answer. You build a degradation ladder, not a dependency. Give each model call a timeout and one bounded retry; put a circuit breaker in front of the provider; and define fallbacks in advance — a second provider or region, a smaller self-hosted model, a cached answer, or a queued job. Keep the fallback warm and tested, because an untested fallback is a second outage. Alert on the primary’s burn rate so you degrade before users notice.

Follow-up: “What is wrong with just retrying?” Retries handle transient blips and do nothing for a sustained outage — worse, they add load to a service that is already struggling. Retries plus a breaker plus a fallback is what covers both the blip and the outage.

Trap. Saying “we use a redundant provider” without naming the routing rule, the health check, or the failure that flips between them. Two providers with no failover logic is one provider with extra steps.

2. What is a circuit breaker, and how does it differ from a retry?

Answer. A retry tries the same call again, hoping the failure was transient. A circuit breaker stops calling a dependency entirely once its error rate crosses a threshold, so you fail fast and protect capacity. It has three states: closed (calls pass), open (calls fail fast), and half-open (a few probe calls test recovery). The breaker is about protecting the caller and the dependency; the retry is about surviving a blip.

Follow-up: “What can go wrong with a breaker?” Flapping. If the threshold is too low or the window too short, it opens on normal noise. Use a minimum request count in the window and a half-open probe rate, and add hysteresis before fully closing.

Trap. Configuring a breaker with no minimum sample size. Ten requests with one error is 10%, and tripping on that takes a healthy service out for no reason.

3. How do reliability and cost conflict, and how do you resolve it?

Answer. Reliability work often costs more: retries add calls, redundancy adds idle capacity, and fallbacks run second systems. Cost work can hurt reliability: aggressive caching serves stale answers, cheap models have worse failure tails, and tight timeouts reject slow-but-correct requests. You resolve it by measuring the unit economics — cost per successful task — and by choosing explicit thresholds. For example, allow retries only for idempotent calls, cap total retry spend per task, and alert when cost per successful task rises.

Follow-up: “Where would you start?” With the per-task cost ceiling and the degradation ladder. The ceiling stops the catastrophic runaway; the ladder means cost pressure degrades quality gracefully instead of causing an outage.

Trap. Treating the two as separate teams’ problems. Cost decisions are reliability decisions, and vice versa, because both act on the same request path.

4. What does least privilege mean for an AI agent, and how do you enforce it?

Answer. The agent acts on behalf of a user, so it should hold only the permissions that user has, only for the task at hand, and only for as long as needed. Enforce it at a policy gateway: authenticate the caller, resolve tenant and roles, and authorise every tool call and data access against that identity. Use short-lived scoped credentials, not long-lived keys, and re-check on each call, because the model can be manipulated by injected text.

Follow-up: “Why not give the agent the service account’s permissions?” Because then prompt injection becomes privilege escalation. A service account usually has broad access; if the model can be tricked into using it, an attacker inherits that access. The user’s narrow identity bounds the blast radius.

Trap. Treating the LLM as a security principal. The model is neither authenticated nor trustworthy; it is a component that can be persuaded. Authorisation belongs to deterministic code outside it.

5. When do you require human approval, and what does that cost you?

Answer. Require approval for irreversible or high-impact actions: moving money, deleting data, sending external communications, and writing to production. The agent proposes and a human disposes. The cost is throughput and latency, plus the risk that reviewers rubber-stamp a queue of proposals. Mitigate with risk tiers — auto-approve low-risk reversible actions, require a human for the rest — and make the approval show exactly what will change.

Follow-up: “How do you keep the queue from becoming a bottleneck?” Right-size the tier boundaries with data: measure how often humans override the agent, and auto-approve the categories where they almost never do. Never auto-approve just to reduce the queue.

Trap. Approving the whole plan rather than the specific action. A reviewer who clicks “approve” on a paragraph of agent reasoning is not a control; show the concrete side effect and require a decision on it.

6. What is the difference between monitoring and observability, and what do you instrument for an agent?

Answer. Monitoring answers known questions with fixed dashboards. Observability lets you ask new questions after the fact. For an agent, instrument trace-first: one trace per request, spans per model and tool call, and attributes for tenant, agent, tool, model, prompt version, token counts, cost, and outcome. Add metrics for golden signals and evals for quality. The prompt version and tool sequence are the attributes that make a bad run reproducible.

Follow-up: “What do you do about PII in traces?” Redact at the source, before the data leaves the service. Store hashes or references where possible, apply retention limits, and never put credentials or raw user content in span attributes.

Trap. Logging only the final answer. The answer alone cannot tell you which retrieval, tool, or prompt produced it — which is exactly the information you need during an incident.

7. How do you control cost when the workload is agentic and open-ended?

Answer. Five controls: a per-request token ceiling, a per-task cost ceiling enforced inside the loop, a per-tenant quota, caching for repeats, and routing to the cheapest model that can do the job. Add a global daily kill switch, and alert on projected burn rather than raw spend. Track cost per successful task, because failures still consume tokens and can dominate the total.

Follow-up: “Why enforce the ceiling inside the loop and not at the gateway?” Because an agent makes many calls over time, and the gateway sees one call at a time. Only the loop knows the running total for the task, so only the loop can stop before it overspends.

Trap. Watching average cost per call. An agent’s cost lives in its tail — the loop that never terminates. Averages hide exactly the runs that break the budget.

8. A quality regression and a cost spike happen at the same time. How do you debug both?

Answer. Start from one trace, because both signals usually come from one root cause: a prompt or config change. Check the prompt version and model version against the last good period; then check routing (are more requests going to the expensive or weak model?), then retrieval (did chunking or index change?), then cache hit rate (a drop raises cost and can change quality). Fix in that order, and use the trace attributes to confirm.

Follow-up: “How do you keep this from happening again?” Gate prompt and model changes behind an offline eval plus a canary, and watch cost per successful task alongside quality during the canary. Version every prompt and model, and store the version on every trace.

Trap. Fixing the symptom you can see. Lowering cost by forcing a weaker model will hide the real regression and often make the cost worse, because failures still consume tokens.

Remember this

  • The request path is the spine; the four concerns wrap all of it. Design them together, not in four later phases.
  • Reliability is bounded retries plus breakers, bulkheads, and a tested fallback ladder. Never retry a non-idempotent write without an idempotency key.
  • Security puts authorisation in deterministic code outside the model. The model is a trust boundary, not a principal; least privilege is what bounds prompt injection.
  • Observability is trace-first, with prompt version, tenant, model, and cost on every span. Redact secrets and PII at the source.
  • Cost is a reliability signal for agents. Enforce budgets inside the loop, alert on projected burn, and measure cost per successful task.
