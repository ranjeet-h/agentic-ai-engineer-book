Multi-Tenant Architecture

Interview answer (say this first). Multi-tenancy is one system serving many customers while keeping their data, compute, and identity separate. There are three models: silo (a dedicated stack per tenant, strongest isolation, highest cost), pool (all tenants share the stack and are separated by a tenant_id, cheapest, weakest isolation), and bridge (shared application with some per-tenant resources, the middle ground). Choose by tenant count, isolation requirement, and cost sensitivity — large regulated tenants get silos, thousands of small tenants share a pool, and mixed portfolios use a bridge. Whatever the model, the tenant id must come from the authenticated token, never from the request body. Enforce it in one place, give every tenant its own keys, quotas, and cost attribution, and defend the shared pool against noisy neighbours with per-tenant rate limits and fair scheduling. The core trade is always the same: isolation buys safety and costs efficiency.

Note:

Verified. Every runnable example on this page was executed offline in plain Python (Python 3.14). No infrastructure or network was used. Cost figures use illustrative token prices and are labelled as such.

Why this exists

A single-tenant system stores one customer’s data and assumes every request is for that customer. Adding a second customer breaks all of it:

  • Data bleeds. A query that filters by id instead of tenant_id returns another customer’s row. One missing WHERE clause is a breach.
  • One tenant starves the rest. A single customer’s bulk job saturates the GPU pool, and everyone else’s latency spikes. These are noisy neighbours.
  • Costs are invisible. The bill arrives as one number. You cannot tell which tenant drove the usage, so you cannot price or defend the service.
  • Identity is confused. Two tenants can have a user named admin. If identity is not scoped by tenant, one can act as the other’s.
  • Configuration collides. Tenant A wants a cautious model and a strict prompt; tenant B wants the opposite. A single global prompt cannot serve both.
  • Compliance differs. One tenant demands data residency and a dedicated encryption key; another is happy with shared infrastructure.

Multi-tenancy is the set of design decisions that answer all of these at once. It is a first-class architecture concern, not a field you remember to add later.

Note:

The one-sentence purpose. Serve many customers from one system by making the tenant a first-class dimension in every layer — data, compute, identity, keys, quota, and cost.

Three distinctions drive every decision:

  • Isolation vs efficiency. A silo is safest and most expensive; a pool is cheapest and riskiest. Most systems pick a model per tenant tier, not one for the whole product.
  • Shared schema vs shared database vs shared infrastructure. You can share a table with a tenant_id, share a database with a schema per tenant, or share nothing. Each step up buys isolation and costs utilisation.
  • Tenant identity vs user identity. A user belongs to one or more tenants. Authorize the user within a tenant, not the user alone, or a valid user of tenant A can read tenant B.

The core idea

Think of an apartment building.

A pool is a shared building where every apartment uses the same utilities and the same front door. It is cheap per unit and efficient, but one neighbour’s loud party is everyone’s problem, and the front door must check that you enter only your own apartment. The tenant_id is the apartment number, and it must be checked at the door, not trusted from the visitor.

A silo is a detached house per family. Maximum privacy, maximum cost, and the family can renovate however it likes. Large or regulated tenants want this.

A bridge is a building with shared common areas but private apartments and private storage. Most real portfolios end up here: shared application, private database for the tenants who pay for it.

How it works

  1. Resolve the tenant at the edge. Read it from the authenticated token or a verified subdomain, not from a request body or header the client can forge.
  2. Propagate tenant context everywhere. Carry the tenant id in a context object through the request, the agent run, every tool call, and every database query.
  3. Enforce the tenant filter in one place. A data-access layer that always adds the tenant predicate, or database row-level security, is far safer than every query remembering to filter.
  4. Scope identity to a tenant. A user’s roles are roles within a tenant. Verify membership before authorizing any action.
  5. Derive per-tenant keys. Never reuse one encryption key across tenants. Derive a data key per tenant from a master secret, and support rotation.
  6. Apply per-tenant quotas and rate limits. Requests per second, tokens per day, concurrent runs, and storage. Quotas prevent one tenant from consuming the system.
  7. Protect against noisy neighbours. Use fair scheduling or per-tenant queues. A single bulk job must not starve interactive traffic.
  8. Attribute cost per tenant. Tag every model call and tool call with the tenant id, then sum usage and apply prices. Without this you cannot price the service or find the heavy users.
  9. Keep prompts and configuration per tenant. Store system prompts, model choice, and policy flags as tenant rows. Resolve them at the start of each run.
  10. Route to different models per tier. A premium tenant may get a stronger model and a dedicated endpoint; a free tenant a smaller one.
  11. Make every write carry the tenant id. Writes are where leaks become breaches. The data layer should reject a write whose tenant does not match the context.
  12. Support onboarding and offboarding. Creating a tenant sets up config, keys, quotas, and an admin. Deleting one removes every trace, provably.
  13. Test isolation automatically. A suite that inserts data as tenant A and asserts tenant B cannot read, update, or delete it, run in CI on every change.
  14. Measure utilisation to pick the model. If silos sit at 10 percent utilisation, the isolation is not paying for itself. If a pool shows repeated leaks or noisy-neighbour incidents, isolation is overdue.

The syntax you will use

Tenant context from the token, never the body. This one rule prevents a whole class of breaches.

from dataclasses import dataclass

@dataclass(frozen=True)
class TenantContext:
    tenant_id: str          # from the verified token claim
    user_id: str
    scopes: frozenset       # resolved from IdP roles, within this tenant

def context_from_token(claims: dict) -> TenantContext:
    return TenantContext(
        tenant_id=claims["tenant"],       # do NOT read this from the request body
        user_id=claims["sub"],
        scopes=frozenset(resolve_scopes(claims.get("roles", []))),  # mapping from the IdP
    )

A data layer that always filters by tenant. The store is bound to a tenant context, so the caller cannot forget the predicate or write into another tenant’s partition.

class PoolStore:
    def __init__(self, context, table):
        self.context = context          # the tenant this request is bound to
        self.table = table              # shared pool storage; rows tagged tenant_id

    def _assert_tenant(self, tenant_id):
        if tenant_id != self.context.tenant_id:
            raise PermissionError("cross-tenant write blocked")

    def insert(self, row):
        self._assert_tenant(row["tenant_id"])   # write must match the context
        self.table.append(dict(row))

    def update(self, row_id, patch, tenant_id):
        self._assert_tenant(tenant_id)
        for r in self.table:
            if r["tenant_id"] == tenant_id and r["id"] == row_id:
                r.update(patch)
                return 1
        return 0

    def delete(self, row_id, tenant_id):
        self._assert_tenant(tenant_id)
        before = len(self.table)
        self.table[:] = [r for r in self.table
                         if not (r["tenant_id"] == tenant_id and r["id"] == row_id)]
        return before - len(self.table)

    def query(self, predicate=lambda r: True):
        # the tenant predicate is applied by the store, not by the caller
        return [r for r in self.table
                if r["tenant_id"] == self.context.tenant_id and predicate(r)]

Per-tenant key derivation. One master secret, a distinct key per tenant and purpose.

import hmac, hashlib

def tenant_key(master: bytes, tenant_id: str, purpose: str) -> str:
    return hmac.new(master, f"{tenant_id}:{purpose}".encode(),
                    hashlib.sha256).hexdigest()

A per-tenant quota. Consume only while under the limit; otherwise deny and count it.

class Quota:
    def __init__(self, limit):
        self.limit = limit
        self.used = 0
        self.denied = 0

    def consume(self, amount):
        if self.used + amount > self.limit:
            self.denied += 1
            return False
        self.used += amount
        return True

Cost attribution. Tag usage with the tenant, then apply prices per tenant.

def attribute_cost(usage_by_tenant, price_in=3.0, price_out=15.0):
    return {
        tenant: round((u["in"] / 1e6) * price_in + (u["out"] / 1e6) * price_out, 4)
        for tenant, u in usage_by_tenant.items()
    }

Max-min fairness for noisy neighbours. Equal share first, then redistribute what small tenants leave.

def max_min_fair(demand, capacity):
    result, remaining, free = {}, dict(demand), capacity
    while remaining:
        share = free / len(remaining)
        small = {t: d for t, d in remaining.items() if d <= share}
        if not small:                      # nobody fits: split the rest equally
            for t in remaining:
                result[t] = share
            break
        for t, d in small.items():
            result[t] = d
            free -= d
            del remaining[t]
    return result

An isolation test. Insert as one tenant, then prove another tenant can neither read nor write its rows.

def _blocked(fn):
    try:
        fn()
        return False
    except PermissionError:
        return True

def isolation_suite():
    table = []                                        # one shared pool
    t1 = PoolStore(TenantContext("t1", "u1", frozenset()), table)
    t2 = PoolStore(TenantContext("t2", "u2", frozenset()), table)
    t1.insert({"tenant_id": "t1", "id": "a", "v": 1})
    t2.insert({"tenant_id": "t2", "id": "b", "v": 1})
    return {
        "reads_only_own": all(r["tenant_id"] == "t1" for r in t1.query()),
        "cross_tenant_read_blocked": t2.query(lambda r: r["id"] == "a") == [],
        "cross_tenant_update_blocked": _blocked(lambda: t2.update("a", {"v": 9}, "t1")),
        "cross_tenant_delete_blocked": _blocked(lambda: t2.delete("a", "t1")),
        "own_update_works": t1.update("a", {"v": 2}, "t1") == 1,
        "own_delete_works": t1.delete("a", "t1") == 1,
        "t1_rows_after_delete": len(t1.query()),
        "t2_rows_untouched": len(t2.query()),
    }

The loud tenant is capped and the quiet tenant keeps its full request, with the spare capacity handed back to the loud one rather than wasted. That is max-min fairness.

In production

  • Take the tenant id from the token. Accepting it from the request body or an unsigned header is a cross-tenant vulnerability, not a convenience.
  • Enforce isolation in one layer, and cover the shared caches and indexes. A single data-access layer or database row-level security is auditable; dozens of hand-written WHERE tenant_id = ? clauses are not. A cache key or embedding search that ignores the tenant can return another tenant’s content, so namespace both by tenant.
  • Scope identity to a tenant. Check membership before every action. Two tenants can both have a user called admin.
  • Use a distinct key per tenant. Derive data keys from a master secret and support rotation and BYOK where required. One shared key makes one leak everyone’s leak.
  • Set quotas and defend against noisy neighbours. Quota every expensive resource — tokens, concurrent runs, storage, requests per second — because without quotas one tenant defines your peak cost. Add per-tenant queues plus fair scheduling so one bulk job cannot starve interactive traffic.
  • Attribute cost continuously. Tag every model and tool call with the tenant id. Retrofitting attribution after a surprise bill is painful.
  • Keep prompts and model choice per tenant. Store them as configuration rows and resolve at run start. Do not encode a customer in a global prompt.
  • Make offboarding provable. Deleting a tenant must remove data, keys, caches, indexes, backups per policy, and derived artifacts. Write it down and test it.
  • Test isolation in CI. Run a suite that attempts cross-tenant reads and writes with each change. Isolation regressions are silent and expensive.
  • Watch utilisation before choosing silos. Dedicated stacks that run at low utilisation are a cost problem. Revisit the model when the portfolio or requirements change.
  • Plan data residency early. Geography is a hard constraint that shapes the tenancy model; it cannot be bolted on later.
  • Give tenants observability of their own usage. A per-tenant usage view reduces support load and makes quotas understandable.

Interview questions

1. What are the tenancy models, and how do you choose?

Answer. Silo gives each tenant a dedicated stack, the strongest isolation at the highest cost. Pool shares everything and separates by tenant_id and policy, the cheapest with the weakest isolation. Bridge shares the application but gives some tenants dedicated resources such as a database. Choose by tenant count, isolation and compliance requirements, and cost sensitivity. Large regulated tenants get silos, thousands of small tenants share a pool, and mixed portfolios use a bridge per tier.

Follow-up: “Can you mix models in one product?” Yes, and most mature products do. A premium tier gets a bridge or silo while the free tier pools. The per-request tenant context resolves the model.

Trap. Choosing a pool for everything to save money and discovering a compliance requirement that only a silo can meet, after launch.

2. Where should the tenant id come from?

Answer. From the authenticated token or a verified subdomain — a value the client cannot forge. Never from the request body, a query parameter, or an unsigned header. The tenant id is an authorization input, so accepting a client-supplied value lets one tenant act as another. Resolve it once at the edge and put it in the request context.

Follow-up: “What if one user belongs to several tenants?” The token should carry the active tenant, or the user selects one and the server verifies membership before issuing a tenant-scoped token.

Trap. Trusting a tenant_id field in a JSON payload because “only our front end calls this.” Internal and partner callers exist too.

3. How do you isolate tenant data in a shared database?

Answer. Every table that holds tenant data carries a tenant_id, and the tenant predicate is enforced by the data-access layer or by database row-level security, not by each query author. Writes are validated so the row’s tenant matches the request context. Add isolation tests that attempt cross-tenant access on every change. Defense in depth is the goal: the application enforces it and the database can too.

Follow-up: “Why row-level security if the application already filters?” Because a single missed clause is a breach, and RLS is a backstop that a query cannot forget. It also makes audits simpler.

Trap. Filtering only in the “list” endpoints and forgetting the “get by id” path. The single-record read is the most common leak.

4. What is a noisy neighbour, and how do you handle it?

Answer. A noisy neighbour is one tenant whose load degrades service for others, usually by saturating a shared GPU pool, queue, or connection pool. Handle it with per-tenant rate limits and quotas, per-tenant queues or priority classes, and fair scheduling that caps any one tenant’s share. Premium tenants can get dedicated capacity. The principle is that no tenant can consume the resource another tenant needs.

Follow-up: “What is max-min fairness?” Give every active tenant an equal share first, then redistribute the capacity that small tenants did not use. It caps the loud tenant without wasting the resource.

Trap. Relying only on a global rate limit. It protects the system but still lets one tenant consume the entire global budget.

5. How do you attribute and control cost per tenant?

Answer. Tag every model call, tool call, and storage write with the tenant id, then aggregate usage and apply prices per tenant. That gives showback or chargeback. Enforce quotas on the expensive resources so a tenant cannot exceed its plan. Attribution turns one opaque bill into per-tenant unit economics, which you need for pricing, capacity planning, and abuse detection.

Follow-up: “What is hard about attribution?” Shared resources — a warmed cache, a shared retrieval index — have no obvious single owner. Allocate them by a stated rule, and keep the rule visible.

Trap. Attributing cost only to the model call. Retrieval, storage, and long-running workflows can dominate the real cost.

6. How do per-tenant prompts and models work?

Answer. Store prompts, model choice, and policy flags as configuration scoped to the tenant, and resolve them at the start of each run. The run context carries the resolved configuration, so tools and prompts never read a global value. This lets a premium tenant use a stronger model and a cautious prompt while a free tenant uses a smaller one. Keep a safe default for new tenants.

Follow-up: “How do you test per-tenant configuration?” With a golden-trace test per tier: the same input should produce the tier’s expected model and prompt path. Add a test that a missing tenant config falls back to the default, not to another tenant’s.

Trap. Encoding a customer’s special case in a global prompt. It drifts, and it leaks one tenant’s instructions to everyone.

7. How do you test tenant isolation?

Answer. Build a suite that, for each tenant, inserts data and then asserts that a second tenant cannot read, update, or delete it through every path: list, get by id, search, vector retrieval, cache, and export. Run it in CI on every change. Also test that a forged tenant id in the request is ignored in favour of the token, and that quotas and rate limits are enforced per tenant.

Follow-up: “What paths are most often missed?” Vector search and caches, because they are added later and often lack a tenant filter. Export and reporting jobs are a close second.

Trap. Testing isolation manually once. Every new endpoint is a new chance to forget the filter, so the test must run automatically.

8. What is the trade between isolation and efficiency?

Answer. Isolation costs efficiency: a dedicated stack cannot share spare capacity, so utilisation drops and cost per tenant rises. A pool maximises utilisation and lowers cost but requires policy to keep tenants apart and to stop noisy neighbours. The right answer is usually tiered — pool the many small tenants, silo the few large or regulated ones — and revisit the split when utilisation or requirements change.

Follow-up: “When does a pool stop being acceptable?” When a compliance requirement demands separation, when isolation incidents recur, or when a large tenant’s load cannot be contained by quotas. Any of those moves that tenant to a bridge or silo.

Trap. Treating the model as permanent. Tenancy is a decision that should change as the portfolio and the rules change.

Remember this

  • Silo is safe and expensive; pool is cheap and risky; bridge is the middle. Choose per tier, and revisit.
  • The tenant id comes from the token, never the request body.
  • Enforce isolation in one layer, and test it in CI on every path, including vector search and caches.
  • Per-tenant keys, quotas, and cost attribution are what make a shared pool operable.
  • No tenant may consume the resource another tenant needs — quotas plus fair scheduling stop noisy neighbours.
